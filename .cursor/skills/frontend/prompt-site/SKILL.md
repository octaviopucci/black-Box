# World Class Digital Product Engine V6

Invoke with **`/prompt-site`** at the start of any new website, landing, SaaS,
dashboard, or digital product request.

**Visual direction (always apply):** Ultra-modern, calm, tactile. Crafted by an
award-winning designer. Smooth micro-interactions.

### CAMPO OBRIGATÓRIO DE CONTEXTO

Antes de iniciar o projeto, solicite ou utilize os seguintes dados:

- **Nicho / segmento da empresa:** [INSIRA O NICHO AQUI]
- **Nome da empresa / marca:** [INSIRA O NOME AQUI]

## REGRA ABSOLUTA — EXTRAÇÃO DE REALIDADE

Antes de escrever qualquer copy, escolher imagens, definir seções ou tomar
decisões visuais, extraia o máximo possível de informações reais da marca.

Você **não** deve começar criando.
Você **deve** começar investigando.

A primeira etapa do projeto é uma operação de **BRAND INTELLIGENCE EXTRACTION**.

Seu objetivo é descobrir como essa empresa realmente existe no mundo.

- Não como você imagina que ela seja.
- Não como outras empresas do nicho são.
- Não como um template sugeriria.
- Mas como ela **realmente** é.

Quando existir um Instagram oficial da empresa, trate-o como uma das principais
fontes de verdade da marca.

Não analise apenas o perfil superficialmente.
Faça uma varredura profunda de todo o conteúdo publicamente disponível e
relevante.

Analise, quando tecnicamente possível:

### PERFIL

- nome
- username
- bio
- descrição
- categoria
- localização
- links
- informações de contato
- destaques
- identidade visual
- foto de perfil

### FEED

Analise o máximo possível de publicações relevantes, incluindo:

- posts
- carrosséis
- Reels
- vídeos
- campanhas
- lançamentos
- produtos
- serviços
- bastidores
- eventos

- instalações
- resultados
- depoimentos
- promoções
- datas comemorativas
- conteúdos educativos
- conteúdos institucionais

Não observe apenas a estética.
Extraia o contexto comercial e estratégico de cada conteúdo relevante.

### DESTAQUES

Analise todos os destaques públicos relevantes.
Procure informações sobre:

- serviços
- produtos
- preços
- equipe
- localização

- bastidores
- avaliações
- clientes
- processos
- diferenciais

Não ignore essas informações.

### STORIES

Se a resposta for nenhuma dessas: **NÃO USE.**

# 0. REGRA ABSOLUTA — ISOLAMENTO CRIATIVO DO PROJETO

**ESTA É A REGRA MAIS IMPORTANTE DE TODO O PROMPT.**

Antes de iniciar qualquer trabalho, estabeleça uma separação absoluta entre:

**INFRAESTRUTURA DO REPOSITÓRIO**

e

**REFERÊNCIA CRIATIVA DO NOVO PROJETO.**

O repositório pode conter outros websites, SaaS, dashboards, landing pages,
componentes, páginas, layouts, estilos, imagens, textos, design systems e projetos
completamente diferentes.

**VOCÊ NUNCA DEVE USAR NENHUM PROJETO EXISTENTE NO REPOSITÓRIO COMO
REFERÊNCIA CRIATIVA.**

## PROIBIÇÃO ABSOLUTA

Nunca, em hipótese alguma:

- copie layouts de outros projetos
- copie estruturas de páginas
- copie hierarquia visual
- copie composição de seções
- copie estilos
- copie paletas
- copie tipografia por influência de outro projeto
- copie componentes visuais
- copie padrões de cards
- copie headers
- copie footers
- copie menus
- copie hero sections
- copie dashboards
- copie grids
- copie espaçamentos
- copie animações
- copie transições
- copie microinterações
- copie efeitos
- copie arquitetura de navegação
- copie fluxo de UX
- copie padrões de formulário
- copie CTAs
- copie textos
- copie tom de voz
- copie estrutura de conteúdo
- copie organização de informações
- copie soluções de interação
- copie composição responsiva
- copie qualquer decisão estética ou de experiência existente no repositório

- NÃO USE OS OUTROS PROJETOS COMO INSPIRAÇÃO.
- NÃO USE OS OUTROS PROJETOS COMO BENCHMARK VISUAL.
- NÃO USE OS OUTROS PROJETOS COMO PONTO DE PARTIDA.
- NÃO "MELHORE" UM PROJETO EXISTENTE PARA CRIAR O NOVO.
- NÃO FAÇA VARIAÇÕES DE PROJETOS EXISTENTES.
- NÃO MISTURE ELEMENTOS DE PROJETOS EXISTENTES.
- NÃO REUTILIZE UMA ESTRUTURA EXISTENTE SÓ PORQUE ELA PARECE FUNCIONAR.

Mesmo que um projeto existente seja visualmente excelente, ignore-o criativamente.
Mesmo que exista uma página praticamente igual ao que está sendo solicitado, não
a utilize como base.
Mesmo que reutilizar determinada estrutura seja mais rápido, não reutilize.

## O QUE O REPOSITÓRIO PODE SER USADO PARA

O conteúdo existente no repositório pode ser analisado somente quando
tecnicamente necessário, por exemplo para:

- entender dependências
- entender configurações
- identificar framework
- entender integrações
- preservar APIs existentes
- identificar variáveis de ambiente
- entender banco de dados
- preservar autenticação
- entender rotas técnicas
- compreender serviços existentes
- verificar limitações da infraestrutura
- reaproveitar lógica de negócio quando explicitamente necessário
- evitar quebrar funcionalidades existentes

Isso é **análise técnica**, não referência criativa.

Você pode reutilizar infraestrutura técnica quando necessário.
Você **NÃO** pode reutilizar decisões criativas simplesmente porque elas já
existem.

## REGRA DE RESET CRIATIVO

Antes de projetar qualquer interface, assuma mentalmente:

> "Se nenhum dos outros projetos deste repositório existisse, como eu
> construiria esta solução para este negócio?"

Essa é a única perspectiva permitida.

O novo projeto deve nascer das:

1. necessidades do negócio
2. identidade da marca
3. características do produto
4. comportamento dos usuários
5. objetivos de conversão
6. informações reais disponíveis
7. contexto competitivo
8. requisitos funcionais
9. pesquisa
10. estratégia definida para ESTE projeto

Nunca do histórico visual do repositório.

## TESTE DE CONTAMINAÇÃO

Antes de finalizar, faça uma auditoria específica:

- "Se eu removesse mentalmente todos os outros projetos deste repositório, eu
  ainda teria tomado exatamente estas decisões de design?" — Se **não**, redesenhe.
- "Alguma parte deste projeto parece derivada de outro projeto existente?" — Se
  **sim**, redesenhe.
- "Alguma estrutura foi escolhida porque já estava pronta no repositório?" — Se
  **sim**, redesenhe.

- Por que escolher?
- O que acontece depois?
- Qual benefício existe?
- O que diferencia?
- Quais objeções existem?
- Como reduzir risco?
- Qual é o próximo passo?

Todo elemento deve possuir uma função.

Se algo não ajuda compreensão, confiança, navegação, conversão, retenção ou
marca — questione sua existência.

---

# 14. FOTOGRAFIA E IMAGENS

Priorize materiais reais da empresa.

Quando imagens externas forem necessárias, escolha-as de acordo com a direção
de arte definida para este projeto.

Não escolha imagens porque combinam com outro projeto existente no repositório.

Analise:

- iluminação
- composição
- enquadramento
- emoção
- ambiente
- pessoas
- cores
- qualidade
- contexto
- consistência

As imagens devem construir narrativa.

---

# 15. MOTION

Utilize movimento com propósito.

Priorize:

- transições naturais
- feedback visual
- hierarquia
- storytelling
- percepção de qualidade
- orientação espacial

Tecnologias possíveis:

- Framer Motion
- GSAP
- Motion One

Nunca adicione animações apenas para impressionar.

---

# 16. RESPONSIVIDADE

Projete experiências específicas para:

- mobile
- tablet
- notebook
- desktop
- ultra-wide

Reavalie:

- hierarquia
- navegação
- tamanho de elementos
- densidade
- interação
- ordem de conteúdo
- espaçamento
- formulários

Mobile deve ser tratado como experiência própria.

# 17. ACESSIBILIDADE

Garanta:

- contraste adequado
- navegação por teclado
- foco visível
- labels
- semântica HTML
- alt text
- hierarquia correta
- áreas clicáveis adequadas
- suporte a leitores de tela
- reduced motion quando necessário

Acessibilidade não é etapa posterior.

# 18. PERFORMANCE

Priorize:

- lazy loading
- code splitting
- dynamic imports
- cache
- font optimization
- redução de JavaScript
- Server Components quando apropriado
- carregamento progressivo

Evite dependências desnecessárias.

# 21. SEGURANÇA E DADOS

Nunca exponha:

- secrets
- API keys
- tokens
- credenciais
- dados privados
- variáveis sensíveis

Respeite autenticação, autorização e permissões existentes.

---

# 22. REUTILIZAÇÃO DE CÓDIGO

Reutilize código quando isso melhorar:

- estabilidade
- manutenção
- performance
- consistência técnica

Mas diferencie claramente:

**REUTILIZAÇÃO TÉCNICA**

de

**REUTILIZAÇÃO CRIATIVA**

Código utilitário pode ser reutilizado.
Lógica de negócio pode ser reutilizada quando necessário.
Infraestrutura pode ser preservada.

Design, layout, UX, copy e direção visual **não** devem ser herdados de outros
projetos do repositório.

---

# 23. AUDITORIA DE ORIGINALIDADE

Antes de finalizar, execute uma auditoria específica.

## CONTAMINAÇÃO DO REPOSITÓRIO

- Alguma tela foi baseada em outro projeto?
- Algum layout foi reaproveitado?
- Algum componente visual foi escolhido porque já existia?
- Alguma composição foi copiada?
- Alguma navegação foi herdada?
- Alguma animação foi reutilizada por conveniência?
- Alguma decisão estética veio de outro projeto?

Se sim: **REFAÇA.**

## QUALIDADE

- Parece template?
- Parece clone?
- Parece um projeto de IA?
- Existe algum bloco genérico?
- Existe alguma seção sem função?
- Existe alguma interação desnecessária?
- Existe alguma oportunidade de melhorar a conversão?
- Existe alguma oportunidade de aumentar percepção de valor?
- Existe alguma fricção?
- Existe alguma inconsistência?

Se sim: **REFINE.**

---

# 24. AUDITORIA FINAL

Antes de considerar o trabalho concluído, verifique:

## Estratégia

- O produto resolve o problema correto?
- O objetivo principal está claro?
- A arquitetura favorece esse objetivo?

## Marca

- A identidade está correta?
- A personalidade está presente?
- A experiência parece exclusiva?

## UX

- O fluxo é intuitivo?
- As informações aparecem na ordem correta?
- Existe fricção desnecessária?

## UI

- Existe consistência?
- Existe hierarquia?
- Existe sofisticação?
- Existe personalidade?

## Conversão

- Os CTAs são claros?
- As objeções foram tratadas?
- Existe confiança suficiente?
- O próximo passo é óbvio?

## Conteúdo

- A copy é específica?
- Existem informações inventadas?
- Os textos parecem humanos?

## Tecnologia

- O código está organizado?
- O sistema é escalável?
- A performance é adequada?
- A acessibilidade foi considerada?

## Originalidade

A pergunta mais importante:

> "Este projeto poderia existir exatamente assim se todos os outros projetos do
> repositório nunca tivessem existido?"

Se a resposta não for um **SIM absoluto**, continue trabalhando.

---

# 25. REGRA DE OURO

Nunca entregue algo apenas porque:

- funciona
- está bonito
- está rápido
- está completo
- está responsivo

Isso é apenas o mínimo.

O objetivo é criar algo que pareça:

- intencional
- estratégico
- exclusivo
- memorável
- coerente
- premium
- feito para aquela empresa

E, acima de tudo:

**NÃO COPIE O REPOSITÓRIO.**

- O repositório é apenas infraestrutura.
- A identidade da empresa é a fonte da verdade.
- O usuário é a fonte da experiência.
- A estratégia é a fonte das decisões.
- Os dados são a fonte das informações.
- A criatividade deve nascer do zero.

Cada novo projeto começa com uma tela mentalmente em branco.
Nenhum projeto existente no repositório deve influenciar sua estética, UX,
arquitetura visual, copy, composição ou direção criativa.

**CONSTRUA DO ZERO.**
